下班前给 Claude Code 布置了一个较大的重构任务，想着让它在终端里自己跑。第二天回来，终端停在某一步，提示连接出错或请求超时，前面的工作进度还在，后面却没了下文。这种"agent 长任务中断"的体验，比普通网页断一下要折磨人得多，因为它一次会话里要发出几十甚至上百次请求，任何一次失败都可能让整条链路停下。

关于编辑器内的联网问题，之前写过[GitHub Copilot、Claude Code 联网总断的指南](/zh/2026/09/29/github-copilot-claude-code-bian-cheng-jia-su/)；这篇专门讲命令行场景里特有的几件事。

## 为什么命令行里的任务更容易断

和浏览器不同，终端里的程序有几个先天特点：

- 不一定使用系统代理。浏览器通常会读取操作系统的网络设置，命令行程序却往往只认环境变量，或者直接走默认网络。所以"浏览器里能上，终端里不行"是很常见的现象。
- 请求次数多、持续时间长。agent 需要不断读取文件、调用模型、再根据结果继续，每一轮都要联网，累计起来对线路稳定性的要求远高于普通聊天。
- 流式输出依赖长连接。模型边生成边返回时，一条连接要保持较长时间，网络抖动一下就可能被重置。
- 夜间或离开电脑期间，电脑休眠、WiFi 切换都会让连接静默掉线，而你不在场，无法及时重试。

| 现象 | 常见原因 | 可以先做什么 |
|------|------|------|
| 启动就报连接失败 | 终端没有走加速通道 | 检查终端的代理环境变量与网络出口 |
| 跑一阵后超时 | 线路在高峰期抖动 | 换节点，或使用智能路由 |
| 离开电脑后中断 | 休眠、网络切换导致掉线 | 关闭自动休眠，使用 tmux 等保持会话 |
| 偶发报错后整个任务停止 | 单次请求失败未重试 | 分阶段下达任务，便于从中间恢复 |

具体报错含义、重试策略和支持的配置项，请以 Anthropic 官方文档和 Claude Code 的最新说明为准，这里只讲通用原则。

## 先确认终端的流量真的走对了路

这是整个排查里关键、也常被忽略的一步。

### 终端里的程序是否继承了代理设置？

很多命令行工具会读取 `HTTPS_PROXY`、`HTTP_PROXY` 这类环境变量。先看看当前终端里有没有设置：

```bash
env | grep -i proxy
```

如果输出为空，而你的加速客户端提供的是本地代理端口，那么终端里的程序可能根本没有经过它。可以在当前终端临时设置后再运行：

```bash
export HTTPS_PROXY=http://127.0.0.1:端口号
```

端口号以你所用客户端实际显示为准。是否支持这些变量，同样请对照 Claude Code 官方文档确认。

### 用 curl 验证出口是否畅通

```bash
curl -v https://api.anthropic.com -o /dev/null
```

只要能看到 TLS 握手完成并收到服务端的响应头，就说明这个终端到服务端的路是通的；如果卡在连接或握手阶段，说明问题在网络路径，而不是 Claude Code 本身。

## 让长任务更耐得住波动

线路排查清楚之后，从"流程设计"上再加几道保险：

1. **用 tmux 或 screen 保持会话**。这样即使 SSH 断开或终端窗口被关掉，任务进程也不会被一起带走，回来 `tmux attach` 就能接着看。
2. **关闭自动休眠**。长任务期间让电脑保持唤醒，避免网络适配器被系统关闭。
3. **把大任务拆成阶段**。每完成一个阶段做一次提交，哪怕中途断开，也只需要从上一个检查点继续，而不是从头再来。
4. **开启 Kill Switch**。如果你通过 TonBo VPN 访问，开启 Kill Switch 后，连接掉线时会立即中断网络而不是悄悄切回普通线路，既保护数据，也让你更早发现"断了"，原理可以参考[Kill Switch 是什么](/zh/2026/10/04/kill-switch-shi-shen-me-duan-xian-bao-hu/)。
