周五下班前想把一个新项目拉下来跑一遍：`git clone` 停在 `Receiving objects: 8%` 十分钟不动，换成 `pip install -r requirements.txt` 又是一连串 `Retrying`，最后 `npm install` 报了 `ETIMEDOUT`。三个工具、三种报错，其实多数时候指向同一类问题——到目标服务器的链路质量不稳。

这篇不堆配置，而是给一套从外到内的排查顺序。

## 先判断：慢在哪一层

包下载慢，大致分成四个阶段，每个阶段的表现不一样：

| 阶段 | 典型表现 | 常见原因（示意） |
|------|---------|----------------|
| 域名解析 | 命令长时间没有任何输出 | DNS 响应慢或解析结果不佳 |
| 建立连接 | 报 timeout、connection reset | 链路丢包、出口线路拥堵 |
| 传输数据 | 开始了但速度忽快忽慢，甚至归零 | 带宽被占用、中途丢包重传 |
| 本地处理 | 下载完成后卡在解压、编译 | 与网络无关，是磁盘或 CPU 问题 |

先用一条命令确认“连接”这一层是否正常：

```
curl -v https://github.com
```

看输出里 `Connected to` 出现得快不快、TLS 握手有没有卡住。如果连这一步都要十几秒，说明问题在链路而不是 Git 或 pip 本身。再用 `nslookup github.com` 看域名解析是否迅速返回。

## 为什么 GitHub 克隆会卡住

`git clone` 默认会把完整历史一起拉下来，仓库越大，持续传输的时间越长，中途只要线路抖动一次，就可能出现长时间停滞。

两个常用的缓解办法：

1. **浅克隆**：`git clone --depth 1 <仓库地址>`，只取当前这一次提交，体积通常小很多，之后需要历史再用 `git fetch --unshallow` 补齐
2. **打开调试输出**：`GIT_CURL_VERBOSE=1 git clone <仓库地址>`，能看到卡在哪个请求上

如果浅克隆都经常中断，就不要继续硬重试了。反复超时多半是到目标服务器的出口线路不稳，可以先换一个节点试一遍，或者用 TonBo VPN 的智能路由让这类请求走更稳定的链路，再重新克隆。这一步经常比调任何 Git 参数都管用。

## pip 安装超时怎么处理

pip 的问题通常有两种：连接超时，和下载中途断开。

先看看用的是哪个源：

```
pip config list
pip install -v <包名>
```

`-v` 会输出详细过程，能看出是在访问索引页还是在下载具体文件时卡住。

然后可以做三件事：

- 加大超时与重试：`pip install --default-timeout=100 --retries 10 <包名>`
- 如果包比较大，先单独下载再安装：`pip download <包名>`，下载完成后用本地文件安装
- 检查是否配置了公司或学校的内部镜像源，确认它当前可以访问

需要注意，更换软件源属于“绕开问题”而不是“解决线路问题”。如果官方源本身就是你要用的，稳定的网络通道依然是更根本的办法。

## npm 安装超时怎么处理

npm 的依赖树通常很深，一次安装会发起几百甚至上千个请求，所以哪怕丢包率不高，累计起来也容易触发超时。

可以按这个顺序检查：

1. `npm config get registry`，确认当前使用的源
2. `npm install --fetch-timeout=120000 --fetch-retries=5`，延长单次请求等待时间并增加重试次数
3. `npm cache verify`，排查本地缓存是否损坏
4. 以 `npm install --verbose` 重新运行，观察是哪个包反复失败

如果每次失败的包都不一样，说明是整体链路不稳，而不是某个包的问题；如果始终是同一个包，则更可能是该包所在的 CDN 节点与当前出口的连通性有问题，换节点后往往会变化。

## 什么时候该换线路，而不是继续调参数

给出一个简单的判断标准：

- 调大超时、重试之后偶尔能成功，但速度依然很不稳定：倾向于换线路
- `curl -v` 连接阶段就很慢或经常失败：倾向于换线路
- 同一台机器上，别的地区的网站都很快，只有某几个域名慢：倾向于换线路，并配合分流让开发工具走加速、其他流量直连
- 报错是认证失败、404、版本冲突：与网络无关，请回到命令本身排查

## 总结

克隆慢、pip 超时、npm 超时，往往是同一条链路问题的不同表现。排查顺序可以记成：先用 `curl -v` 和 `nslookup` 判断卡在解析还是连接，再用浅克隆、增加超时与重试等方式降低对链路波动的敏感度；如果这些都只是“偶尔成功”，就应该把注意力放回线路本身，换节点或使用 TonBo VPN 的智能路由，往往比继续调参数更有效。
