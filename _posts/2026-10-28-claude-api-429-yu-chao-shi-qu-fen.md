批量处理文档的脚本跑到一半，日志里蹦出一串错误：前几条是 429，后面几条变成了 timeout。很多人会把它们笼统归为"API 不稳定"，然后给代码加一个"失败就重试三次"。结果 429 越重试越多，超时也没有好转。

原因在于，这两类错误的本质不同：一个是"服务端收到了你的请求，但让你慢一点"，另一个是"请求根本没能顺利往返"。分清楚，处理才有针对性。

## 一句话区分：有没有拿到响应

**429 是服务端明确返回的状态码，含义是请求过于频繁，被限流。** 既然服务端能返回这个状态码，说明你的网络是通的，请求已经到达，也已经被处理过判断逻辑。

**超时是客户端在等待时间内没有收到完整响应。** 它不说明服务端怎么想，只说明"来回这一趟没走完"，可能是网络路径不稳，也可能是服务端当时处理很慢。

| 对比项 | 429 | 超时 |
|------|------|------|
| 是否收到服务端响应 | 是，有明确状态码 | 否，或响应不完整 |
| 网络是否畅通 | 通常是畅通的 | 不确定，需排查 |
| 常见诱因 | 请求频率或用量超出限额 | 线路抖动、丢包、DNS 异常、服务端繁忙 |
| 重试策略 | 先降速、按提示等待 | 先排查链路，再有限重试 |

限额的具体数值、响应头里携带哪些提示信息，不同账号和时期都可能不同，请以 Anthropic 官方文档和控制台里的说明为准。

## 怎么判断你遇到的是哪一种

### 看日志里的错误类型

在代码里把状态码和异常类型分开记录。能读到 HTTP 状态码的，就属于"有响应"一类；抛出的是连接超时或读取超时异常，属于"无响应"一类。两种情况混在同一个 `except` 里，会给后期排查带来很大麻烦。

### 单独测一次连通性

用一个很简单的方式检查网络本身是否畅通，不需要带任何密钥：

```bash
curl -v -o /dev/null https://api.anthropic.com
```

只要能看到 TLS 握手完成并拿到任意 HTTP 状态码，就说明网络路径是通的。如果卡在 `Connecting to` 或握手阶段迟迟没有结果，问题在链路层，与限流无关。想看耗时分布，可以加上 `-w` 参数输出各阶段时间：

```bash
curl -sS -o /dev/null -w "dns=%{time_namelookup}s connect=%{time_connect}s tls=%{time_appconnect}s total=%{time_total}s\n" https://api.anthropic.com
```

哪一段数值明显偏大，哪一段就是瓶颈。DNS 慢，可以先 `nslookup api.anthropic.com` 看解析是否稳定；connect 慢，多半是线路本身的问题，丢包和延迟的读法可参考[延迟、丢包、抖动分别是什么](/zh/2026/10/15/yan-chi-diu-bao-dou-dong-kan-dong-ping-ce-shi/)。

### 对照请求时间点

429 往往出现在请求密集的时段，比如并发开得很高的前几秒；超时则更随机，和网络状态相关。把错误时间戳和并发量放在一起看，规律通常很清楚。

## 两类问题分别怎么处理

### 遇到 429

- **降低并发和速率**，给请求队列加上节流，而不是让所有任务同时起跑。
- **采用指数退避加随机抖动**的重试方式：每次失败后等待的时间逐步增加，并加入一点随机量，避免多个任务同一时刻再次撞上限额。
- **如果响应里带有建议等待时间的信息，优先遵循它**，具体字段以官方文档为准。
- 用量长期触顶，应考虑申请更高额度或优化请求本身，比如合并请求、缩短不必要的上下文。

### 遇到超时

- **先确认超时设置合理**。生成较长内容时，等待时间可能比普通接口长，超时值设得过小会造成误报。
- **检查本机出口**：终端里的程序是否继承了正确的网络设置，这一点在[Claude Code 长任务中断](/zh/2026/10/18/claude-code-ming-ling-xing-chang-ren-wu-zhong-duan/)里讲过类似的思路。
- **线路层面不稳时**，反复重试只会放大失败。这里反复超时，多半是出口线路在丢包，可以先换一个节点验证；长时间跑的批处理任务，建议走 TonBo VPN 的 IEPL 国际专线，并开启 Kill Switch，让断线时任务停下来而不是悄悄走错路径。
- 超时重试要设上限，且保证请求是可安全重复的，避免重复计费或重复写入。

## 常见问题

### 429 和超时同时出现，先处理哪个？

先处理超时。网络不通时，限流的判断没有意义，也很难观察到真实的限流表现。链路稳定之后，再根据 429 出现的频率调整并发。

## 小结

429 是"到了，但请你慢点"，超时是"没走完"。前者调速率和重试策略，后者查链路和出口。两类错误分开记录、分开处理，批处理任务的成功率会比简单重试高得多。
