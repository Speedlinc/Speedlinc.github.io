有一类故障让人格外摸不着头脑：同一个网站，首页能打开，点进内容页就一直转圈；聊天软件里文字消息正常，一发图片就失败；网速测试结果也不差，偏偏某几个页面怎么也加载不出来。重启路由器、换浏览器都没用。

如果这些现象在连着 VPN 或者换了一条宽带之后才出现，不妨查一查 MTU。

## MTU 是什么？

**MTU（最大传输单元）是网络链路上，一个数据包允许携带的最大字节数。** 以太网的标准值通常是 1500 字节。比这更大的数据，发送方会把它切成多个包再发出去。

可以把它想象成快递的箱子尺寸：每个箱子有最大容量，货物太大就要拆箱。但这条路上如果有一段"窄门"，比标准尺寸还小，带着标准大箱子的快递就过不去了。

## 为什么会出现"窄门"

常见原因有两类。

- **宽带拨号方式**：部分宽带使用 PPPoE 拨号，会占用一部分包头空间，通常有效 MTU 为 1492。
- **隧道和加密封装**：VPN 会给每个数据包再套一层外壳，这层外壳也占空间，通常是几十个字节，具体取决于所用协议。于是实际能承载内容的空间，比 1500 小。

如果这时系统仍按 1500 去发包，包就会"超规格"。理想情况下，路径上的设备会告知发送方"请改小一点"，但有些网络设备会丢弃这类提示，发送方就一直收不到反馈，大包也始终发不过去。

| 数据类型 | 包大小 | 在 MTU 过小的链路上 |
|------|------|------|
| 文字消息、网页请求 | 通常很小 | 能正常通过 |
| 图片、大网页内容 | 容易填满整个包 | 可能被丢弃，表现为卡住 |
| 加密握手的某些步骤 | 常有较大数据包 | 可能握手失败，页面打不开 |

这就解释了"小数据正常、大数据失败"的怪现象，也是"部分网页打不开"的常见成因之一。上表为通常情况的原理性描述。

## 怎么检测当前链路的合适 MTU

核心思路是：发出禁止分片的 ping 包，逐步调大数据量，看多大会失败。

在 Windows 上：

```bash
ping -f -l 1472 example.com
```

在 macOS 上：

```bash
ping -D -s 1472 example.com
```

在 Linux 上：

```bash
ping -M do -s 1472 example.com
```

这里的 1472 是 1500 减去 28 字节包头得到的数值。如果提示数据包需要分片或直接失败，就逐次减小这个数字（比如 1450、1430、1400），直到不再报错。**能通过的最大数值加上 28，就是这条链路上大致可用的 MTU。**

## 怎么设置 MTU

先说明：多数 VPN 客户端会自行调整虚拟网卡的 MTU，大部分情况下你不用手动改。只有在检测结果明显偏小、而且问题可以稳定复现时，再考虑下面的调整，并且记下原值方便还原。

查看当前值：

```bash
# Windows
netsh interface ipv4 show subinterfaces

# macOS
networksetup -listvalidMTUrange en0
```

修改示例（把 1400 换成你实测得到的数值，网卡名称按实际情况替换）：

```bash
# Windows（需要管理员权限）
netsh interface ipv4 set subinterface "以太网" mtu=1400 store=persistent

# macOS
sudo networksetup -setMTU en0 1400
```

调整后重新打开出问题的页面验证。如果没有改善，就把数值还原为原来的值，不要继续往小调，MTU 过小反而会降低传输效率。

## 小结

MTU 决定了一个数据包能装多大。链路上存在"窄门"而系统仍然发大包时，就会出现"小数据正常、大数据卡死"的现象，表现为部分网页打不开、图片发不出去。用禁止分片的 ping 就能大致测出合适值，调整时记得先记下原值。日常使用中，选择会自动处理封装开销的客户端，比手动调参更稳妥。
