凌晨三点，一个批量处理文本的脚本跑到一半，日志里开始成片地出现 `timeout`、`Connection reset`、`Read timed out`。代码没改，密钥没变，昨天还一切正常。这时候容易走偏的做法，是对着代码一行行怀疑自己。

调用 OpenAI API 失败，原因其实可以分成三层：域名解析、网络出口、客户端的重试与超时策略。每一层都有标准的验证方法，按顺序走一遍，通常十几分钟内就能定位。

## 第一步：先判断是"服务端问题"还是"连接问题"

在动手之前，先看两件事：

1. **官方状态页**：确认服务当前有没有正在处理的故障。具体页面与说明以官方文档为准。
2. **错误类型**：HTTP 状态码（如 4xx、5xx）说明请求已经到达服务端并得到了回应；而超时、连接被重置、握手失败，说明请求根本没有顺利到达，或回应没有顺利回来。

这个区分很关键：前者要看账号额度、请求格式、限流策略；后者才是本文要讲的网络层排查。

## 第二层排查：DNS 解析

域名解析慢或解析到不理想的地址，是超时的常见原因。用标准命令验证：

```bash
nslookup api.openai.com
```

观察三点：能否正常返回地址、返回是否很慢、多次查询结果是否反复变化。解析慢或失败时，可以尝试：

- 刷新本地 DNS 缓存：Windows 使用 `ipconfig /flushdns`，macOS 使用 `sudo dscacheutil -flushcache`。
- 在系统或网络设置里换一个更稳定的 DNS 服务。
- 对比不同网络（有线、手机热点）下的解析结果。

关于 DNS 请求本身可能出现的问题，可以参考[DNS 泄漏是什么？一分钟自查与防范方法](/zh/2026/07/17/dns-xie-lou-shi-shen-me/)，了解解析流程在加速环境下应该如何走。

## 第三层排查：网络出口与链路

解析正常之后，要看请求能不能顺利跑到服务端。先用 `curl -v` 看连接各阶段：

```bash
curl -v https://api.openai.com/v1/models
```

这条命令不带密钥，会得到未授权的响应，但这正是我们要的：只要能看到完整的 TLS 握手和 HTTP 回应，说明链路是通的。重点观察卡在哪一步：

| 卡住的阶段 | 说明 | 可能原因 |
|-----------|------|---------|
| 域名解析之前就卡住 | DNS 慢或失败 | 本地 DNS 异常 |
| `Trying ...` 后长时间无反应 | TCP 连接建立失败 | 出口线路拥堵、丢包 |
| 已连接但 TLS 握手迟迟不完成 | 握手包丢失 | 链路质量差 |
| 握手成功但响应很久才回来 | 往返延迟高或服务端繁忙 | 线路绕路、服务端负载 |

再用 `ping` 和 `traceroute`（Windows 是 `tracert`）观察延迟与路径：

```bash
ping -c 20 api.openai.com
traceroute api.openai.com
```

部分服务可能不响应 ping，不要仅凭 ping 不通就下结论，应结合 curl 的表现一起判断。如果多次测试里连接阶段波动大、时好时坏，说明出口线路不稳定。

这类场景下，服务器经常部署在云厂商的机房里，跨境链路的稳定性直接决定调用成功率。如果你的开发机或服务器所在网络到该服务的路径反复超时，可以考虑让这部分跨境流量走更稳定的线路，例如使用 TonBo VPN 的 IEPL 国际专线，并配合智能路由让 AI 平台的请求走优化过的路径。部署在服务器上时，建议先在小范围验证稳定性，再决定是否纳入正式流程。

## 第四层：重试与超时策略也要自查

有时网络并没有坏到不可用，只是你的客户端把一次小抖动放大成了整批失败。检查这几项：

### 超时时间设得是否合理？

连接超时与读取超时应分开设置。连接超时可以短一些，读取超时对生成类请求要给足时间，尤其是长文本输出。具体默认值与推荐设置，以官方 SDK 文档为准。

### 是否做了有间隔的重试？

对超时与偶发的 5xx 错误，推荐使用**指数退避加随机抖动**的重试：第一次等一小会儿，第二次等得更久，每次再加一点随机量，避免所有失败请求在同一时刻一起重试。

### 是否有并发控制？

并发数过高会让本地出口拥堵，也容易触发服务端的限流。把并发降低到合理范围，往往比增加重试次数更有效。

### 是否复用了连接？

使用 SDK 提供的 HTTP 客户端并复用连接，可以减少反复握手的开销；每个请求都新建连接，在网络不稳时更容易失败。

## 一份简明的排查清单

1. 看状态页，区分服务故障与连接故障。
2. `nslookup` 验证解析，必要时刷新 DNS 缓存。
3. `curl -v` 观察卡在哪个阶段，`ping` 和 `traceroute` 观察延迟与路径。
4. 换一个网络环境对比，确认是否与出口线路相关。
5. 检查超时、退避重试、并发和连接复用的设置。
6. 线路确实不稳时，改用更稳定的跨境线路，再重新测试。

## 总结

OpenAI API 超时不是一个单一问题，而是 DNS、出口、客户端策略三层共同决定的结果。先分清服务端与连接问题，再按"解析、链路、重试"的顺序逐层验证，配合 curl 与 traceroute 找到卡住的位置。线路层面不稳时，换用更稳定的跨境线路，加上合理的退避重试，调用 API 的成功率会稳定得多。
